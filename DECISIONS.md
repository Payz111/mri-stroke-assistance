## ADR-001: Выбор датасета для V1

**Дата:** 2026-02-04  
**Статус:** ✅ Принято

**Проблема:** Какой датасет использовать для MVP сегментации инсульта?

**Варианты:**
1. ISLES 2022 — DWI/ADC/FLAIR, 250 кейсов, multi-center
2. Acute Stroke 2,888 — больше данных, но требует доступа через ICPSR
3. ISLES 2015 — старый, меньше данных

**Решение:** ISLES 2022

**Причина:**
- Современный бенчмарк (2022)
- Открытый доступ (Zenodo)
- Мульти-центр/мульти-вендор → хороший тест на generalization
- Именно те модальности, которые нужны (DWI/ADC/FLAIR)
- Есть community для сравнения результатов

## ADR-002: Выбор датасета для V2 (Perfusion)

**Дата:** 2026-02-04  
**Статус:** ✅ Принято

**Проблема:** MRI PWI или CT Perfusion для V2?

**Варианты:**
1. ISLES 2015/16/17 — MRI PWI, но старые и ограниченные
2. ISLES 2024 — CTP (CT Perfusion), современный, хорошо структурирован

**Решение:** ISLES 2024 (CTP)

**Причина:**
- Более доступные и качественные данные
- CTP чаще используется в клинической практике для triage
- Перфузионная логика (core/penumbra) одинакова для MRI PWI и CTP
- Follow-up infarct mask как ground truth — идеально для evaluation

## ADR-003: Архитектура модели сегментации

**Дата:** 2026-02-04  
**Статус:** ✅ Принято

**Проблема:** Какую архитектуру использовать для baseline?

**Варианты:**
1. nnU-Net v2 — SOTA, но сложный в настройке
2. MONAI 3D U-Net — проще, хорошая интеграция
3. Attention U-Net — добавляет attention gates
4. Swin UNETR — transformer-based

**Решение:** MONAI 3D U-Net (baseline), затем возможно nnU-Net

**Причина:**
- Быстрее начать и итерировать
- Полный контроль над кодом
- Достаточно для хороших результатов
- Можно позже сравнить с nnU-Net

## ADR-004: Подход к генерации отчёта

**Дата:** 2026-02-04  
**Статус:** ✅ Принято

**Проблема:** Как генерировать текст отчёта без галлюцинаций?

**Варианты:**
1. End-to-end image → text (VLM) — современно, но галлюцинирует
2. Template-based из JSON — контролируемо, но менее "естественно"
3. LLM-парафраз JSON с валидатором — компромисс

**Решение:** Template-based + валидатор (MVP), затем LLM-парафраз (v1.1)

**Причина:**
- **0 галлюцинаций** — жёсткое требование
- Каждое утверждение в тексте должно иметь источник в JSON
- Template гарантирует это
- Позже можно добавить LLM для "красивого" текста, но с валидатором

## ADR-005: Определение vascular territory

**Дата:** 2026-02-04  
**Статус:** ✅ Принято

**Проблема:** Как определять сосудистую территорию (MCA/ACA/PCA/VB)?

**Варианты:**
1. Atlas-based mapping — регистрация к атласу территорий
2. Rule-based по анатомии — центр масс → грубое правило
3. Learned classifier — обучить на данных

**Решение:** Rule-based (MVP), atlas-based (v1.1)

**Причина:**
- Быстрее реализовать
- Достаточно для MVP (грубая классификация)
- Можно уточнить позже с атласом

## ADR-006: QC и политика отказа

**Дата:** 2026-02-04  
**Статус:** ✅ Принято

**Проблема:** Что делать при плохом качестве входных данных?

**Варианты:**
1. Всегда давать prediction (с low confidence)
2. No-score при failed QC
3. Partial output (что можем, то выдаём)

**Решение:** No-score при critical QC fail

**Причина:**
- Безопасность важнее полноты
- Лучше честно сказать "не могу" чем угадывать
- В клинике неуверенный ответ опаснее отсутствия ответа
- QC report всё равно информативен

## ADR-008: Experiment tracking

**Дата:** 2026-02-04  
**Статус:** ✅ Принято

**Проблема:** Как трекать эксперименты?

**Варианты:**
1. MLflow — self-hosted, open source
2. Weights & Biases — cloud, красивый UI
3. TensorBoard — простой, встроен в PyTorch
4. Просто логи — минимально

**Решение:** MLflow (primary), TensorBoard (optional)

**Причина:**
- Бесплатный, self-hosted
- Артефакты, параметры, метрики в одном месте
- Легко сравнивать эксперименты
- Model registry для версионирования

## ADR-009: V2 perfusion thresholds

**Дата:** 2026-02-04  
**Статус:** ✅ Принято

**Проблема:** Какие пороги использовать для core/penumbra?

**Решение:** Конфигурируемые defaults
- Hypoperfusion: Tmax ≥ 6 seconds
- Core: rCBF ≤ 30%
- Target mismatch: core < 70ml, ratio > 1.8, mismatch > 15ml

**Причина:**
- Широко используемые в литературе и практике
- Можно менять через конфиг
- Не "зашиваем" в код

## ADR-010: Позиционирование продукта (safety)

**Дата:** 2026-02-04  
**Статус:** ✅ Принято

**Проблема:** Как позиционировать систему с точки зрения безопасности?

**Решение:** Clinical Decision Support (CDS), NOT autonomous diagnosis

**Принципы:**
- Human-in-the-loop обязателен
- "Draft for review", не "final diagnosis"
- Никаких рекомендаций по лечению
- Evidence-linked (маски/срезы для проверки)
- Честные disclaimers и limitations
